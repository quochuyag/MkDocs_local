00Tổng quan & ma trận lựa chọn

⚙Chuẩn bị môi trường (common cho mọi giải pháp)

4 script scripts/common/ chạy trên tất cả nodes trước khi triển khai bất kỳ giải pháp HA nào. Thứ tự cứng:

  1. Source biến môi trường — scripts/common/env.sh chứa IPs, hostnames, ports, mật khẩu, version. Mọi script đều source file này ở đầu. 
    # Sửa env.sh nếu thực tế khác:
export NODE1_IP=192.168.20.11
export RS_NAME=rs0
export MONGO_ADMIN_PWD='ChangeMe!Admin#2026'
export MONGO_MAJOR=7.0       # hoặc 8.0
  2. Prepare OS — 00-prepare-os.sh: /etc/hosts, swap off, THP off (yêu cầu cứng của WiredTiger), sysctl, ulimit, NTP. 
    bash scripts/common/00-prepare-os.sh   # chạy trên mọi node
  3. Install MongoDB — 01-install-mongo.sh: thêm repo, cài mongodb-org, start mongod chế độ standalone tạm. 
    bash scripts/common/01-install-mongo.sh   # mongod sẽ chạy tạm trên 127.0.0.1:27017
  4. Firewall — 02-firewall.sh: mở 27017/27018/27019/27020. 
    bash scripts/common/02-firewall.sh
  5. KeyFile internal auth — 03-keyfile.sh: sinh 1024-byte base64 secret. Phải copy thủ công sang TẤT CẢ nodes (cùng 1 nội dung) — sai → secondary refuse join. 
    # Trên mgmt (hoặc node1):
bash scripts/common/03-keyfile.sh
# Copy sang các node khác:
scp /etc/mongodb/keyfile root@node2:/etc/mongodb/keyfile
scp /etc/mongodb/keyfile root@node3:/etc/mongodb/keyfile
# Trên mỗi node:
chown mongodb:mongodb /etc/mongodb/keyfile && chmod 400 /etc/mongodb/keyfile
  6. TLS (tuỳ chọn, khuyến nghị prod) — 04-tls-self-signed.sh: sinh CA + server cert. Production thay bằng PKI thật. 
    bash scripts/common/04-tls-self-signed.sh
Quan trọng — KeyFile KeyFile phải byte-identical trên mọi member của cùng cluster. Trong Vagrant lab, file vagrant/provision/keyfile được sinh 1 lần qua make keyfile và copy lên cả 4 VMs qua provisioner trust.

01Replica Set (PSS — Primary + 2 Secondary)

Native Auto-failover 3 nodes Default cho mọi prod

Giải pháp HA mặc định của MongoDB. Mọi runbook sau (PITR, Hidden, Multi-region) build trên top của Replica Set. 3 nodes form quorum: tolerate 1 fault, election tự động ~10 giây.

Kiến trúc

┌────────────────────────────────────┐ ┌──▶│ App + MongoDB Driver │ │ │ ?replicaSet=rs0&readPref=nearest │ │ └────────────┬───────────────────────┘ discovery │ │ TCP :27017 topology │ │ │ ┌──────────┴───────────┐ │ │ │ │ ▼ ▼ ┌──────────────────┐ ┌──────────────────┐ │ node1 :27017 │ │ node2 :27017 │ │ PRIMARY pri=2 │◀─────▶│ SECONDARY pri=1 │ │ rs.isWritable() │ oplog │ RO │ └────────┬─────────┘ └─────────┬────────┘ │ oplog tailing │ ▼ ▼ ╲ ╱ ╲ ┌────────────────┘ ╲ │ ▼ ▼ ┌──────────────────┐ │ node3 :27017 │ │ SECONDARY pri=1 │ └──────────────────┘ Election: Khi PRIMARY mất → SECONDARY (optime mới nhất) ứng cử → cần ≥2/3 votes → PRIMARY mới trong ~10s → Driver tự reconnect (topology stream)

Khi nào dùng

✅ Dùng được

  • OLTP dataset < 1 TB
  • 1 data center hoặc 2 DCs LAN (< 5ms RTT)
  • Workload đa số read, write < 50k/sec
  • App có thể connect string list 3 hosts

❌ Không phù hợp

  • Dataset > 1 TB (chuyển sang Sharded — Sol-03)
  • Cross-region latency > 50ms (xem Sol-06 multi-region)
  • Cần multi-master write (Mongo không có; Sharded có thể parallel)

Tiền đề

  • 3 nodes đã chạy scripts/common/00-prepare-os.sh, 01-install-mongo.sh, 02-firewall.sh
  • KeyFile /etc/mongodb/keyfile giống nhau trên 3 nodes
  • Hostname/IP resolve được giữa các nodes (getent hosts node2)

Tình huốngPhản ứng

02PSA Topology (Primary + Secondary + Arbiter)

Compromise 2 data + 1 vote Trade-off cao

PSA = 2 data nodes + 1 arbiter (chỉ vote, không lưu data). Tiết kiệm 1 host disk. Đánh đổi: write concern w:majority có thể block khi 1 data node down.

Kiến trúc

┌──────────────────────────────────┐ ┌──▶│ App + Driver │ │ │ replicaSet=rspsa │ │ └─────────┬────────────────────────┘ │ │ :27017 │ ┌──────┴──────┐ │ │ │ │ ▼ ▼ │ ┌────────────────────┐ ┌────────────────────┐ │ │ node1 :27017 │ │ node2 :27017 │ │ │ PRIMARY (data) │◀─▶│ SECONDARY (data) │ │ │ pri=2 votes=1 │ │ pri=1 votes=1 │ │ └─────────┬──────────┘ └─────────┬──────────┘ │ │ oplog │ │ └────────┬───────────────┘ │ │ heartbeat (vote-only) │ ▼ │ ┌─────────────────────┐ │ │ node3 :27020 │ └────────────│ ARBITER (no data) │ │ pri=0 votes=1 │ └─────────────────────┘ Quorum: ✅ 1 data + arbiter = 2/3 → election OK ⚠ Nhưng w:majority cần 2 DATA writes — arbiter không thoả → 1 data node down ⇒ writes w:majority BLOCK

Khi nào dùng (và khi nào KHÔNG)

✅ Dùng được

  • Chỉ có 2 host data + 1 host rẻ (jump/mgmt)
  • Workload chấp nhận w:1 hoặc đôi khi block ngắn với w:majority
  • Dev/staging muốn tiết kiệm

❌ KHÔNG nên

  • App yêu cầu w:"majority", j:true 100% thời gian
  • Cluster > vài trăm GB (arbiter không donor recovery)
  • Production critical — MongoDB khuyến nghị PSS, không PSA
MongoDB ≥ 5.0 PSA + writeConcern bloat Với PSA và w:"majority", nếu secondary mất, primary tiếp tục accept writes nhưng không commit majority → WiredTiger giữ all uncommitted snapshots → cache bloat → restart primary có thể rollback writes. Theo dõi: 
mongodb_mongod_replset_member_replication_lag{state="SECONDARY"} > 60
mongodb_mongod_replset_member_health{state="SECONDARY"} == 0

Runbook triển khai

  1. Config 2 data nodes (node1, node2) 
    # Trên node1 và node2:
bash /vagrant/scripts/psa/node-config.sh data
# Tạo /etc/mongod-data.conf + systemd unit mongod-data.service
# port 27017, replSet=rspsa
  2. Config arbiter (node3 hoặc mgmt) 
    # Trên node3:
bash /vagrant/scripts/psa/node-config.sh arbiter
# port 27020, dataDir riêng, chỉ giữ metadata vote
  3. Initiate PSA (chỉ trên node1) 
    bash /vagrant/scripts/psa/initiate-psa.sh
    rs.initiate({
  _id: 'rspsa',
  members: [
    { _id: 0, host: '192.168.20.11:27017', priority: 2 },
    { _id: 1, host: '192.168.20.12:27017', priority: 1 },
    { _id: 2, host: '192.168.20.13:27020', arbiterOnly: true }
  ]
});
  4. Verify 
    mongosh -u admin -p --eval 'rs.status().members.forEach(m => print(m.name + " " + m.stateStr))'
# kỳ vọng: PRIMARY, SECONDARY, ARBITER

Runbook — Failure scenarios PSA

Tình huốngPhản ứng
1 data node down Election OK (1 data + arbiter = 2/3). PRIMARY mới được bầu (hoặc giữ nguyên).
⚠ Writes w:majority BLOCK. Workaround tạm: chuyển w:1 cho non-critical workload.
Arbiter down 2/2 data sống = majority. Cluster vẫn writable. Restart arbiter, không cần resync.
Mất cả 2 data nodes Cluster offline. Khôi phục từ backup (Sol-05).
Chuyển PSA → PSS (nâng cấp) 
rs.add('node4:27017');           // add data node thứ 3
rs.remove('node3:27020');         // bỏ arbiter

03Sharded Cluster (horizontal scale)

Scale write Auto-failover per shard ★★★★ complex Dataset > 1 TB

Sharded cluster = mongos router (stateless) + config server replica set (metadata) + N shard replica sets (data). Mỗi shard tự HA bằng election như Sol-01.

Kiến trúc đầy đủ

┌────────────────────────────────────────┐ ┌──▶│ App (connect string trỏ vào mongos) │ │ └────────────┬───────────────────────────┘ │ │ :27017 │ ┌─────────▼──────────────┐ │ │ mongos #1 (router) │ ← stateless, deploy ≥2 để HA │ │ mgmt :27017 │ │ └─────────┬──────────────┘ │ │ reads metadata + routes ops │ ▼ │ ┌─────────────────────────────────┐ │ │ Config Server Replica Set │ │ │ cfgrs (3 members, role=configsvr)│ │ │ node1:27019 node2:27019 node3:27019 │ │ Stores: chunks, balancer state, RS topology │ └─────────────────────────────────┘ │ │ │ ┌───────────┼───────────┐ │ ▼ ▼ ▼ ┌────────────────┐ ┌────────────────┐ ┌────────────────┐ │ Shard 1 RS │ │ Shard 2 RS │ │ Shard N RS │ │ shard1rs │ │ shard2rs │ │ shardNrs │ │ ┌──────────┐ │ │ ┌──────────┐ │ │ ┌──────────┐ │ │ │ PRIMARY │ │ │ │ PRIMARY │ │ │ │ PRIMARY │ │ │ │node1:27018│ │ │ │node4:27018│ │ │ │nodeN:27018│ │ │ └────┬─────┘ │ │ └────┬─────┘ │ │ └────┬─────┘ │ │ ┌────▼─────┐ │ │ ┌────▼─────┐ │ │ ┌────▼─────┐ │ │ │SECONDARY│ │ │ │SECONDARY│ │ │ │SECONDARY│ │ │ │node2:27018│ │ │ │node5:27018│ │ │ │ ...│ │ │ └────┬─────┘ │ │ └────┬─────┘ │ │ └──────────┘ │ │ ┌────▼─────┐ │ │ ┌────▼─────┐ │ └────────────────┘ │ │SECONDARY│ │ │ │SECONDARY│ │ │ │node3:27018│ │ │ │node6:27018│ │ Data partitioned │ └──────────┘ │ │ └──────────┘ │ theo shard key └────────────────┘ └────────────────┘ {userId: "hashed"} │ │ │ └── Balancer di chuyển chunks └──── giữa shards để cân bằng Lab mapping: 3 VMs chạy đồng thời cfgsvr :27019 + shard1 :27018 mgmt chạy mongos :27017

Khi nào dùng

✅ Cần shard

  • Dataset > 1 TB hoặc working set vượt RAM 1 node
  • Write throughput > 50k/sec (vượt khả năng 1 primary)
  • Cần data residency theo region (zone sharding — Sol-06)
  • Multi-tenant với hot tenants tách shard riêng

❌ Không cần shard

  • Dataset < 500 GB → Replica Set đủ
  • Read-heavy → tăng secondary reads + cache
  • Chưa có shard key strategy → setup sai thì pain

Tiền đề

  • 3 nodes đã chạy scripts/common/00..02
  • KeyFile chung trên tất cả nodes + mgmt
  • mongos host (mgmt) cài mongodb-org-mongos + mongodb-mongosh

Runbook triển khai

  1. Config Server Replica Set 
    # Trên node1, node2, node3 (port 27019, role=configsvr):
bash /vagrant/scripts/sharded-cluster/config-server-setup.sh

# Trên node1 — init RS + tạo admin user:
bash /vagrant/scripts/sharded-cluster/config-server-setup.sh --init
    Script ghi /etc/mongod-cfg.conf với sharding.clusterRole: configsvr, systemd unit mongod-cfg.service.
  2. Shard 1 Replica Set 
    # Trên node1, node2, node3 (port 27018, role=shardsvr):
bash /vagrant/scripts/sharded-cluster/shard-setup.sh

# Trên node1 — init RS:
bash /vagrant/scripts/sharded-cluster/shard-setup.sh --init
  3. mongos router (trên mgmt) 
    bash /vagrant/scripts/sharded-cluster/mongos-setup.sh
    Script ghi /etc/mongos.conf với configDB string: 
    sharding:
  configDB: cfgrs/node1:27019,node2:27019,node3:27019
security:
  keyFile: /etc/mongodb/keyfile
  4. Add shard + tạo users + enable sharding 
    bash /vagrant/scripts/sharded-cluster/add-shard.sh
    // Script chạy các lệnh sau qua mongos:
sh.addShard('shard1rs/node1:27018,node2:27018,node3:27018');

// Tạo users
db.getSiblingDB('admin').createUser({...});
db.getSiblingDB('appdb').createUser({user:'appuser', ...});

// Enable sharding + shard collection mẫu:
sh.enableSharding('appdb');
sh.shardCollection('appdb.events', { userId: 'hashed' });
  5. Verify 
    mongosh "mongodb://admin:@mgmt:27017/admin" --eval 'sh.status({verbose:false})'
    Kỳ vọng: 1 shard shard1rs, database appdb partitioned, collection events hashed.
  6. App connection 
    # KHÔNG có replicaSet param — driver tự nhận diện sharded cluster:
mongodb://appuser:@mgmt:27017/appdb
# Nhiều mongos: mongos1,mongos2,mongos3:27017

Runbook — Disaster scenarios

Tình huốngTác động + phản ứng
Primary của 1 shard chết Election trong shard (~10s). mongos phát hiện qua heartbeat, route lại. App không thấy gì lạ.
Config server quorum loss (2/3 cfg down) Cluster READ-ONLY — không sửa được metadata. Khôi phục node config từ backup hoặc resync.
1 shard mất hoàn toàn (3/3 down) Data của shard đó không accessible. Reads/writes vào chunks shard khác vẫn OK. Khôi phục shard từ backup (Sol-05).
mongos chết App reconnect sang mongos khác (nếu connection string có nhiều mongos).
Shard key — chọn sai = pain cả vòng đời cluster
  • hashed: chia đều nhưng range query inefficient.
  • Compound {tenant:1, ts:1}: tốt cho time-series multi-tenant.
  • Phải có index trên prefix shard key trên mọi collection sharded.
  • Test trên staging với data thật trước. Đổi shard key (Mongo 5.0+) tốn kém.

04Hidden + Delayed member

Anti-mistake Add-on cho RS Dedicated backup host

Bổ sung trên top Replica Set (Sol-01) — chuyển 1 secondary thành hidden + priority=0 + delayed N giây. Mục đích: phòng xoá nhầm, dedicated backup host, reporting offline.

Kiến trúc

┌──────────────────────────────────┐ ┌──▶│ App + Driver │ │ │ ?replicaSet=rs0 │ │ └────────────┬────────────────────┘ │ │ :27017 │ ┌─────────┴─────────┐ │ │ │ │ ▼ ▼ ┌──────────────────┐ ┌──────────────────┐ │ node1 :27017 │ │ node2 :27017 │ │ PRIMARY pri=2 │◀──▶│ SECONDARY pri=1 │ └─────────┬────────┘ └─────────┬────────┘ │ oplog │ └───────┬───────────────┘ │ │ (chậm 24h) ▼ ┌─────────────────────────┐ │ node3 :27017 │ │ SECONDARY │ │ pri=0 hidden=true │ ← Driver KHÔNG thấy node này │ delay=86400s (24h) │ ← Replicate chậm 24h └─────────────────────────┘ │ ▼ (chạy backup không impact primary) mongodump --oplog Use cases: 🛡 Lúc 10:00 ai đó deleteMany({}) trên PRIMARY 🛡 Lúc 10:05 alert. Hidden member vẫn còn data của 09:00 (delay 24h) 🛡 mongodump từ node3 → restore selectively lên primary

Khi nào dùng

  • Bảo hiểm xoá nhầm: 30 phút sau khi ai đó db.users.deleteMany({}), vẫn còn data trên delayed secondary để dump.
  • Backup dedicated host: hidden + priority=0 → không serve traffic → chạy mongodump thoải mái không tốn IO primary.
  • Reporting/ETL nightly: hidden member phục vụ 1 job batch qua read pref tag.

Runbook triển khai

  1. Đảm bảo có RS đã chạy (Sol-01)

  2. Trường hợp A — dùng 1 trong 3 members hiện tại

  3. Trường hợp B — thêm node thứ 4 dedicated (khuyến nghị prod)

Runbook — Recovery xoá nhầm

Giả sử lúc 10:00 ai đó db.events.deleteMany({}) trên primary. Alert nhận lúc 10:05:

  1. Stop replication trên delayed member để "đóng băng" state lúc 09:00 
    // Trên node3 (delayed member):
db.adminCommand({ fsync: 1, lock: true });
  2. Dump collection từ delayed member 
    mongodump --host node3:27017 -u admin -p ... \
  --authenticationDatabase admin \
  --db appdb --collection events \
  --out /tmp/recovery
  3. Unlock delayed member 
    db.fsyncUnlock();
  4. Restore lên primary (collection riêng để không đè data hiện tại) 
    mongorestore --host node1:27017 -u admin -p ... \
  --nsFrom 'appdb.events' \
  --nsTo 'appdb.events_recovered' \
  /tmp/recovery
  5. Merge / swap collection trong app logic

Trade-offs

Khía cạnhTác động
VotersHidden member vẫn vote mặc định. Set votes:0 nếu không muốn.
DiskDelayed member chứa full data chậm N giây. Disk ≈ primary.
Oplog windowPhải > delay + buffer. Delay 24h → oplog ≥ 48h.
FailoverHidden + pri=0 không bao giờ thành primary tự động. DR cần force-reconfig.
Promote delayed → primary (DR scenario, mất ≤ 24h data)

05Backup & Point-In-Time Recovery

RPO < 5 phút 3 phương thức Bắt buộc cho mọi prod

3 chiến lược backup chính: logical (mongodump), filesystem snapshot (LVM/EBS), Percona PBM / Ops Manager. PITR đạt được bằng cách combine snapshot + oplog tail liên tục.

So sánh phương thức

Phương thứcTốc độStoragePITRKhi nào dùng
mongodump --oplog Chậm (re-read mọi doc) Nén tốt ✅ (--oplogReplay) Cluster nhỏ < 500 GB
Filesystem snapshot (LVM/EBS) Nhanh (~vài phút) ≈ disk usage ✅ (+ oplog tail) Production size lớn
Percona PBM / Ops Manager Tích hợp Variable ✅ Sharded cluster, multi-RS

Kiến trúc Backup + PITR

node1 PRIMARY ──┬──▶ oplog (continuous log of writes) │ │ replicate ▼ node2 SECONDARY ◀──── mongodump --oplog (cron daily 02:00) │ ▼ /var/backups/mongo/ ├── dump-20260515T020000Z/ ← base full dump ├── dump-20260516T020000Z/ └── oplog/ ├── oplog-...02:05.bson.gz ← every 5 min ├── oplog-...02:10.bson.gz ├── oplog-...02:15.bson.gz └── ... PITR đến T = 14:32:17 ngày 15/05: 1. mongorestore dump-20260515T020000Z với --oplogLimit=T 2. Replay tuần tự oplog-*.bson.gz có toT ≤ T 3. Result: data state chính xác lúc 14:32:17

Phương thức A — Logical (mongodump)

  1. Full dump consistent snapshot 
    # Chạy từ hidden member (Sol-04) để giảm impact:
bash /vagrant/scripts/backup-pitr/mongodump.sh node3:27017
# Output: /var/backups/mongo/dump-20260515T120000Z/
    Cờ --oplog dump kèm window oplog trong lúc dump → restore lại đạt consistent point cuối dump.
  2. Restore toàn bộ 
    bash scripts/backup-pitr/mongorestore.sh /var/backups/mongo/dump-20260515T120000Z node1:27017
  3. Schedule cron daily 
    # /etc/cron.d/mongo-backup
0 2 * * * root bash /vagrant/scripts/backup-pitr/mongodump.sh node3:27017 \
  >> /var/log/mongo-backup.log 2>&1

Phương thức B — Filesystem snapshot

Tiền đề: dbPath nằm trên LVM logical volume (hoặc EBS volume nếu AWS). Chạy trên SECONDARY (không phải primary) — fsyncLock() block writes.

  1. Snapshot 
    # Trên node2 (secondary):
bash scripts/backup-pitr/fs-snapshot.sh --vg vg_mongo --lv lv_data
# Pipeline: fsyncLock → lvcreate snapshot → fsyncUnlock
  2. Copy snapshot đi storage backup 
    mount /dev/vg_mongo/lv_data-snap-20260515T120000Z /mnt/snap
tar czf /var/backups/mongo/snap-20260515T120000Z.tar.gz -C /mnt/snap .
umount /mnt/snap
lvremove -f /dev/vg_mongo/lv_data-snap-20260515T120000Z
# Hoặc upload lên S3.
  3. Restore (full) 
    systemctl stop mongod
mv /var/lib/mongodb /var/lib/mongodb.broken
mkdir /var/lib/mongodb
tar xzf /var/backups/mongo/snap-20260515T120000Z.tar.gz -C /var/lib/mongodb
chown -R mongodb:mongodb /var/lib/mongodb
systemctl start mongod

PITR — continuous oplog tail + replay

  1. Setup oplog tail (cron mỗi 5 phút) 
    # /etc/cron.d/mongo-oplog
*/5 * * * * root bash /vagrant/scripts/backup-pitr/oplog-tail.sh node2:27017 \
  >> /var/log/mongo-oplog.log 2>&1
    Script lưu state ở ${OPLOG_BACKUP_DIR}/.last-ts và dump oplog từ ts đó tới hiện tại.
  2. Restore tới thời điểm cụ thể (PITR) 
    # Sự cố lúc 14:32:17 UTC ngày 15/05 = 1758804737 Unix.
# Base dump 02:00 cùng ngày + oplog archives mỗi 5 phút.
bash scripts/backup-pitr/pitr-restore.sh \
  /var/backups/mongo/dump-20260515T020000Z \
  1758804737 \
  node1:27017
    Script chạy: restore base dump với --oplogLimit, sau đó apply lần lượt archive oplog có toT ≤ target.
  3. Verify 
    // Check 1 row vừa tạo trước thời điểm cố:
db.events.find({ createdAt: { $lt: ISODate("2026-05-15T14:32:18Z") } })
        .sort({ createdAt: -1 }).limit(1)
Test restore monthly là BẮT BUỘC Backup không test = không backup. Lịch trình đề xuất:
  • Hàng tuần: restore vào sandbox VM, đếm record, checksum 1 collection.
  • Hàng tháng: PITR đầy đủ, app smoke test (login, write, read).
  • Hàng quý: chaos test — destroy primary + restore from backup.

Sharded cluster backup — Percona PBM

Backup nhất quán cho sharded cluster phức tạp (cần đồng bộ snapshot mọi shard + config server). Tự host: dùng Percona Backup for MongoDB (PBM):

# Trên mỗi node + mongos:
apt install percona-backup-mongodb
pbm config --file pbm-config.yml          # storage S3/filesystem
pbm backup --type=physical                 # full backup
pbm backup --type=logical                  # logical
pbm restore <backup-name>
pbm pitr --enable                          # bật continuous oplog backup

06Multi-region / Cross-DC HA / Zone Sharding

DR cross-region RPO < 1 phút Data residency

3 pattern cho multi-region: Stretched RS (1 RS spread nhiều DCs), 5-node stretched (active-active failover), Sharded + Zone sharding (data theo region).

Pattern A — Stretched Replica Set (DR ready)

┌─────────── DC-A (primary region) ───────────┐ ┌── DC-B (DR region) ──┐ │ │ │ │ │ ┌────────────┐ ┌────────────┐ │ │ ┌────────────┐ │ │ │node1 :27017│ │node2 :27017│ │ │ │node4 :27017│ │ │ │PRIMARY pri=2│ │SECONDARY │ │ │ │SECONDARY │ │ │ │ votes=1 │ │pri=1 v=1 │ │ │ │pri=0 v=0 │ │ │ └─────┬──────┘ └─────┬─────┘ │ │ │(DR only) │ │ │ │ │ │ │ └──────┬─────┘ │ │ └───────┬───────┘ │ │ │ │ │ │ oplog (LAN, <5ms) │ │ │ async │ │ ▼ │ │ │ (WAN ~80ms) │ ┌────────────────┐ │ │ │ │ │ │node3 :27017 │ │ │ │ │ │ │SECONDARY pri=1 │◀──────────────────┴──┴──────────┘ │ │ └────────────────┘ │ └──────────────────────────────────────────────┘ │ └──────────────────────┘ 3 voters ở DC-A → election KHÔNG bị ảnh hưởng latency DC-B node4 pri=0,v=0 → chỉ replicate, không vote, không thành primary tự động DR procedure: force-reconfig để promote node4 khi DC-A mất hoàn toàn

Pattern B — 5-node stretched (active-active failover)

┌── DC-A ────────────┐ ┌── DC-B ────────────┐ ┌── DC-C (neutral) ──┐ │ │ │ │ │ │ │ node1 pri=2 v=1 │ │ node3 pri=1 v=1 │ │ node5 :27020 │ │ node2 pri=1 v=1 │ │ node4 pri=1 v=1 │ │ ARBITER v=1 │ │ │ │ │ │ │ └─────────┬──────────┘ └─────────┬──────────┘ └─────────┬──────────┘ │ │ │ └──────────────────────────┼─────────────────────────┘ │ 5 voters, tolerate 1 DC mất → vẫn quorum 3/5 RTT DC-A↔DC-B PHẢI < 250ms cho w:majority reasonable DC-C tiny VM, chỉ chạy arbiter

Pattern C — Sharded + Zone Sharding (data residency)

┌──────────────────────────────┐ │ mongos mỗi DC │ └──────────────┬───────────────┘ │ ┌────────────┴────────────┐ ▼ ▼ ┌────────── DC-A (US) ─────────┐ ┌────────── DC-B (EU) ─────────┐ │ │ │ │ │ Shard A tag=US │ │ Shard B tag=EU │ │ Chứa documents region='us' │ │ Chứa documents region='eu' │ │ ┌──────┐ ┌──────┐ ┌──────┐ │ │ ┌──────┐ ┌──────┐ ┌──────┐ │ │ │node1 │ │node2 │ │node3 │ │ │ │node4 │ │node5 │ │node6 │ │ │ └──────┘ └──────┘ └──────┘ │ │ └──────┘ └──────┘ └──────┘ │ └──────────────────────────────┘ └──────────────────────────────┘ │ │ └──────────┬────────────────────────┘ ▼ ┌────────────────────────────┐ │ Config Server RS │ ← stretched 3 DCs │ (chứa chunk → tag mapping)│ └────────────────────────────┘ Shard key: { region: 1, _id: 1 } sh.addTagRange('appdb.events', {region:'us', _id:MinKey}, {region:'us', _id:MaxKey}, 'US') ⇒ Document có region='eu' KHÔNG BAO GIỜ rời DC-B (compliance)

Tiền đề

  • Đã có RS PSS (Sol-01) hoặc Sharded Cluster (Sol-03)
  • Network: cross-DC latency < 250ms cho stretched RS
  • TLS bắt buộc cho cross-region traffic (common/04-tls-self-signed.sh cho lab)

  • Atlas Global Clusters tự động zone sharding — đáng cân nhắc nếu không muốn tự build.

💡Lời khuyên chung / common pitfalls

1. KeyFile permissions

KeyFile BẮT BUỘC: mode 400 + owner mongodb:mongodb + nội dung byte-identical trên mọi member. Sai 1 trong 3 → mongod refuse start hoặc secondary refuse join. 
# Standard fix:
chmod 400 /etc/mongodb/keyfile
chown mongodb:mongodb /etc/mongodb/keyfile
# Verify checksum giống nhau giữa nodes:
md5sum /etc/mongodb/keyfile

2. THP (Transparent Huge Pages)

MongoDB/WiredTiger yêu cầu tắt THP để tránh thrashing. Script 00-prepare-os.sh đã setup systemd unit disable-thp.service chạy khi boot. Verify: 
cat /sys/kernel/mm/transparent_hugepage/enabled
# Kỳ vọng: always madvise [never]   ← "never" trong []
systemctl status disable-thp.service
# Kỳ vọng: Active: active (exited)

3. Oplog window

Oplog là local.oplog.rs capped collection lưu mọi write trên primary. Khi secondary lag hơn oplog window → phải resync từ đầu (initial sync). Quy tắc ngón tay cái:

  • ≥ 24h window cho cluster nhỏ-trung bình.
  • ≥ delay + 24h khi có delayed member (Sol-04).
  • Mặc định oplogSizeMB: 2048 (2 GB) trong scripts. Production tuỳ throughput, 5-10 GB phổ biến.
  • Theo dõi: bash scripts/replica-set/ops.sh oplog.

4. WiredTiger cache

Mặc định MongoDB lấy max(50% RAM - 1GB, 256MB). Script lab set 1 GB. Production: không quá 50% RAM, để OS file cache có chỗ.

5. Write concern + Read concern

ConcernTrade-offKhi dùng
w:1Nhanh, có thể mất write nếu primary chếtLogs, metrics, non-critical
w:"majority"Slow hơn (cần majority ack), không rollbackOLTP thường
w:"majority", j:trueChậm nhất, đảm bảo journal diskFinancial, audit
readConcern:"local"Có thể đọc data sẽ bị rollbackDefault — đa số case
readConcern:"majority"Chỉ đọc data đã majority commitReporting, billing

6. Connection string driver

  • Replica Set: list ≥2 hosts + replicaSet=rs0 để driver discover topology.
  • Sharded Cluster: trỏ vào mongos, không replicaSet. List nhiều mongos để HA.
  • Atlas: mongodb+srv:// dùng DNS SRV — driver tự discover.
  • retryWrites=true + retryReads=true đều default trong driver 4.0+.

7. Observability mặc định

  • mongodb_exporter (Prometheus): github.com/percona/mongodb_exporter
  • Grafana dashboards: MongoDB Overview (2583), MongoDB Exporter (12079)
  • Alerts essential:
    • mongodb_up == 0
    • mongodb_mongod_replset_member_replication_lag > 60
    • mongodb_mongod_replset_member_state{state!~"PRIMARY|SECONDARY"}
    • Oplog window < 24h
