# 🕵️ Phân Tích Log: Lỗi ORA-19809 Fast Recovery Area Full

**Chế độ**: Phân tích Log (Troubleshooting - Module 16)
**Ngày tạo**: 2026-04-22 15:50:02

## 1. Tình huống sự cố
Vào lúc 3h sáng, tiến trình RMAN Backup Job hàng ngày của bạn bị thất bại. Sáng hôm sau, các ứng dụng phàn nàn rằng database bị treo, không thể thực hiện các thao tác insert/update.
Bạn kiểm tra Alert Log và thấy hàng loạt lỗi sau:

```text
ORA-19815: WARNING: db_recovery_file_dest_size of 107374182400 bytes is 100.00% used, and has 0 remaining bytes available.
************************************************************************
You have following choices to free up space from recovery area:
1. Consider changing RMAN RETENTION POLICY. If you are using Data Guard,
   then consider changing RMAN ARCHIVELOG DELETION POLICY.
2. Back up files to tertiary device such as tape using RMAN
   BACKUP RECOVERY AREA command.
3. Add disk space and increase db_recovery_file_dest_size parameter to
   reflect the new space.
4. Delete unnecessary files using RMAN DELETE command. If an operating
   system command was used to delete files, then use RMAN CROSSCHECK and
   DELETE EXPIRED commands.
************************************************************************
ORA-00257: archiver error. Connect internal only, until freed.
ORA-19809: limit exceeded for recovery files
ORA-19804: cannot reclaim 52428800 bytes disk space from 107374182400 limit
```

## 2. Nhiệm vụ của bạn (DBA)
1. Đọc và giải thích hiện tượng trên. Tại sao database lại bị treo thay vì chỉ hỏng tiến trình backup?
2. Đưa ra Action Plan (gồm các bước xử lý ngay lập tức) để đưa database hoạt động bình thường trở lại.

---

## 3. Hướng dẫn xử lý (Action Plan - Đáp án)

### Phân tích Log (Bắt bệnh)
- **ORA-19809 & ORA-19804**: Cho biết Fast Recovery Area (FRA) đã chạm ngưỡng dung lượng tối đa cấu hình trong tham số `db_recovery_file_dest_size` (trong trường hợp này là 100GB).
- **ORA-00257**: Khi FRA đầy, tiến trình Archiver (ARCn) không thể tiếp tục ghi các Archive logs mới ra đĩa. Do Archive logs không được sinh ra, các Online Redo Logs sẽ không được tái sử dụng (không thể overwrite). Khi tất cả Redo Logs đầy, database sẽ treo các giao dịch (DML) cho đến khi không gian cho Archiver được giải phóng.

### Action Plan (Khắc phục sự cố)

**Bước 1: Tăng tạm thời kích thước FRA (Giải pháp tức thời)**
Để database tiếp tục hoạt động và thoát khỏi tình trạng treo ngay lập tức, cách nhanh nhất là tăng giới hạn FRA (nếu đĩa vật lý của OS vẫn còn trống).
```sql
SQL> ALTER SYSTEM SET db_recovery_file_dest_size = 120G SCOPE=BOTH;
```
*Ngay sau lệnh này, Archiver sẽ tiếp tục đẩy Redo Log thành Archivelog, và DB sẽ giải phóng lock cho ứng dụng.*

**Bước 2: Xóa các bản backup/archivelog đã cũ (Obsolete) bằng RMAN**
Đăng nhập RMAN để dọn dẹp các file rác hoặc các file đã hết hạn lưu trữ (vượt quá retention policy).
```rman
$ rman target /

-- Kiểm tra và xóa file obsolete
RMAN> CROSSCHECK BACKUP;
RMAN> CROSSCHECK ARCHIVELOG ALL;
RMAN> DELETE NOPROMPT OBSOLETE;

-- Nếu vẫn chưa đủ không gian, có thể backup các archivelog ra tape hoặc xóa bớt archivelog đã được backup
RMAN> BACKUP ARCHIVELOG ALL DELETE INPUT;
```

**Bước 3: Giải quyết gốc rễ vấn đề (Tối ưu hóa)**
- Tại sao FRA lại đầy? Kiểm tra xem RMAN Job đêm qua có bị lỗi hay không (có thể do lỗi cấu hình mạng hoặc tape bị offline khiến archivelog không được backup và dọn dẹp).
- Kiểm tra cấu hình `RETENTION POLICY`. Có thể chính sách lưu giữ quá dài so với dung lượng cung cấp.
- Cân nhắc sử dụng cấu hình `CONFIGURE ARCHIVELOG DELETION POLICY TO BACKED UP 1 TIMES TO DEVICE TYPE DISK;` để RMAN tự động dọn archivelog khỏi FRA nếu có áp lực không gian.
