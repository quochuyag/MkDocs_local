# 🕵️ Phân Tích Log: Lỗi ORA-01578 ORACLE Data Block Corrupted

**Chế độ**: Phân tích Log (Troubleshooting - Module 16)
**Ngày tạo**: 2026-04-22 15:50:07

## 1. Tình huống sự cố
Hệ thống báo cáo rằng có một lỗi xảy ra khi ứng dụng truy vấn vào bảng `SALES_DATA`. Người dùng nhận được thông báo lỗi trực tiếp trên giao diện ứng dụng.
Bạn kiểm tra Alert Log của database và thấy dòng sau:

```text
Corrupt block relative dba: 0x01400078 (file 5, block 120)
Bad check value found during multiblock read
Data in bad block:
 type: 6 format: 2 rdba: 0x01400078
 last change scn: 0x0000.00a1b2c3 seq: 0x1 flg: 0x04
 spare1: 0x0 spare2: 0x0 spare3: 0x0
 consistency value in tail: 0xb2c30601
 check value in block header: 0x8f2a
 computed block checksum: 0x3e10
ORA-01578: ORACLE data block corrupted (file # 5, block # 120)
ORA-01110: data file 5: '/u01/app/oracle/oradata/PROD/sales01.dbf'
```

## 2. Nhiệm vụ của bạn (DBA)
1. Đọc và phân tích lỗi `ORA-01578`. Chuyện gì đang xảy ra dưới mức đĩa cứng? Việc offline cả datafile 5 để restore có cần thiết không?
2. Đưa ra Action Plan để sửa chính xác Block số 120 mà không gây gián đoạn cho các Block khác trong file.

---

## 3. Hướng dẫn xử lý (Action Plan - Đáp án)

### Phân tích Log (Bắt bệnh)
- **ORA-01578**: Đây là lỗi vật lý (Physical Corruption). Checksum tính toán được của block khi load vào bộ nhớ (`0x3e10`) không khớp với checksum đã ghi trên block header (`0x8f2a`). Nguyên nhân thường do lỗi ổ cứng (Bad sector), cáp kết nối quang chập chờn, hoặc lỗi bộ điều khiển Storage (HBA).
- **Hệ quả**: Bất kỳ câu lệnh `SELECT` hay `DML` nào vô tình đọc phải Block số 120 của file 5 đều sẽ gặp lỗi và bị văng ra. Tuy nhiên, các block khác trong file 5 vẫn hoạt động bình thường. Việc offline toàn bộ datafile 5 để `RESTORE DATAFILE 5` là hành động "giết gà dùng dao mổ trâu", gây downtime không cần thiết cho toàn bộ tablespace.

### Action Plan (Khắc phục sự cố)

**Bước 1: Xác minh mức độ lan rộng của block lỗi**
Sử dụng RMAN để quét lại file và xác nhận số lượng block hỏng, tránh trường hợp có nhiều block hỏng ngầm khác.
```rman
$ rman target /
RMAN> VALIDATE DATAFILE 5;
```
*Kết quả của lệnh trên sẽ điền thông tin các block lỗi vào view `V$DATABASE_BLOCK_CORRUPTION`.*

**Bước 2: Kiểm tra view hỏng hóc**
Trên SQL*Plus, kiểm tra danh sách các block hỏng:
```sql
SQL> SELECT * FROM V$DATABASE_BLOCK_CORRUPTION;
```
*Nếu chỉ có `FILE# = 5` và `BLOCK# = 120`, bạn có thể yên tâm chuyển qua Bước 3.*

**Bước 3: Thực hiện Block Media Recovery (BMR)**
RMAN hỗ trợ tính năng vô cùng mạnh mẽ: Block Media Recovery (`BLOCKRECOVER`). Nó cho phép restore đúng một (hoặc một số) block từ bản backup và apply redo log để đồng bộ block đó, trong khi database và datafile vẫn đang ONLINE hoàn toàn!
```rman
RMAN> BLOCKRECOVER DATAFILE 5 BLOCK 120;

-- Nếu có nhiều block lỗi từ Bước 2, bạn có thể chạy:
RMAN> BLOCKRECOVER CORRUPTION LIST;
```

**Bước 4: Xác minh kết quả**
Sau khi `BLOCKRECOVER` báo thành công, hãy yêu cầu người dùng hoặc ứng dụng chạy lại câu truy vấn ban đầu. Hoặc bạn có thể truy vấn thử vào bảng chứa block đó.
Truy vấn lại view `V$DATABASE_BLOCK_CORRUPTION` - nó sẽ trả về rỗng (0 rows selected).

### 💡 Bài học kinh nghiệm & Tối ưu:
- RMAN BMR chỉ áp dụng cho Database đang chạy ở chế độ **ARCHIVELOG** và yêu cầu bạn phải có bản full/incremental backup hợp lệ chứa trạng thái tốt trước đó của block này, cùng với đầy đủ archive logs.
- Nếu không có backup, bạn chỉ có cách `DBMS_REPAIR.SKIP_CORRUPT_BLOCKS` (chấp nhận mất dữ liệu trong block đó).
